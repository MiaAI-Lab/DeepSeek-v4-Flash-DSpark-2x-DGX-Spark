## Reasoning per decision

**A base2 → reference, measured despite the gate.** See the memory-gate deviation above. The numbers reproduce yesterday's sp-indexer boot within noise: c=1 pooled 56.6 (yesterday ≈ 55), c=2 42.7 (41.9), c=6 139 (yesterday 131–148), TTFT 4.5 / 18.2 / 78.5 s (4.5 / 17.9 / 76.0), natural 24.7 % / 0.66 (25.4 % / 0.68), numbered 47.3 % (51.2 %). The c=6 aggregate today sits at the low end of yesterday's band (135–141 vs 130–148). The fairness case (c=4, 8K prompts, inflight 1) shows what the default does: the four prefills serialize, so the streams see TTFT 4.7, 9.4, 14.3 and 19.3 s and the early streams decode at 8–11 tok/s while the later prefills run; the last stream decodes alone at 37–40 tok/s. Aggregate 22.6 tok/s.

**B chunk2048 → OFF (memory), unmeasured; C skipped.** Boot gates clean (6/6, alias, sp-indexer on both ranks, KV 16.36 / 15.25 GiB), but head MemAvailable 0.99 GB at the gate and 1.03–1.07 GB over the next three minutes, with head swap use rising from 5.0 to 6.0 GB; worker unaffected (4.5–4.7 GB). That is a 1.5 GB drop against base2 on the same host in the same hour, and it matches the adaptive-chunk finding of 2026-09-02 (2.3 GB vs 3.8–5.2 GB). The mechanism is the same: a larger prefill chunk means larger activation / FlashMLA / indexer workspaces, and on DGX Spark those live in unified memory outside the `GPU_MEMORY_UTILIZATION_TEXT` budget, i.e. in host RAM. The static knob is therefore not a usable fallback for the rejected adaptive patch at util 0.83; a chunk above 1024 needs the host memory found first (report item 1's remaining work). Reverted to 1024; chunk 4096 not attempted per the goal's rule.

**D greedy → OFF (tie).** Correctness and acceptance are fine at both temperatures: natural 25.7 % / 0.69 at temp 0 (base2 24.7 % / 0.66) and 25.0 % / 0.66 at temp 0.6 (base2 25.2 % / 0.66); numbered-word 49.3 % (47.3 %). Decode: c=1 pooled 56.5 (54.7–76.5) vs 56.6 (50.8–67.0), c=6 140 vs 139, c=2 44.5 vs 42.7 — all inside the base2 band, nothing beyond it. The goal's rule for this knob is "keep only if acceptance and decode are ≥ base2 at both temperatures; any drop ⇒ revert"; the temp-0.6 overall acceptance is 0.2 pt lower, which is noise but is not ≥, and there is no target-metric win to justify the sampled-quality risk. Reverted to `probabilistic`. The `DRAFT_SAMPLE_METHOD=probabilistic` line stays in `.env.dspark` as an explicit statement of the compose default.

**E idxlogits512 → OFF (tie).** TTFT 32K 17.92–18.02 s vs base2 18.18–18.29 s (−1.5 %), 128K 77.1 s vs 78.5 s (−1.8 %, one trial each). The goal fixes TTFT noise at ±2 %, so neither number is beyond the band, and yesterday's 128K on the same config ranged 74.4–76.0 s, which brackets today's 77.1 s. 8K unchanged (4.50–4.56 vs 4.47–4.62 s). Decode and acceptance unchanged (c=1 54.2, c=6 142, c=2 42.4; natural 26.3 % / 0.69). Memory 3.94 GB head — the +256 MB workspace did not register on the host. Not a loss, but not a measured win either; reverted to 256 to keep the config at its known state. If a longer-context sweep (256K–900K) is ever run, this is the first knob to retry, since the number of indexer launches per chunk grows with context.

**F inflight2 → ON (fairness win, nothing else moves).** The target metric is the per-stream spread of the c=4 8K case: TTFT spread 9.10–9.21 s vs base2's 14.58–14.79 s (every inflight2 trial below every base2 trial), decode spread 24.2–25.3 vs 29.1–31.3 tok/s, aggregate 25.4 vs 22.6 tok/s (+12 %), worst-stream TTFT 16.5 vs 19.3 s. The cost is the first stream's TTFT (7.4 vs 4.7 s), which is the expected trade: two prefills share the batch instead of one running alone. Everything else stays inside the base2 band: c=1 pooled 53.9 (48.2–56.8; base2 50.8–67.0), c=2 41.6 (base2 40.9–44.3), c=6 139 (base2 135–141), 32K TTFT 17.70–18.26 s, natural 26.7 % / 0.70, numbered 51.1 %, zero errors, MemAvailable 4.12 / 4.73 GB (the best head reading of the day), KV 15.96 / 15.28 GiB (head −0.8 GiB vs base2, within the ±0.6 GiB boot noise seen across all boots). Under the goal's rule (decode not worse, spread ≤ base2's) it stays ON. This settles the PR #90 vs #154 question for this lane: 2 is not a decode regression at c ≤ 6, and it halves the fairness penalty at c=4 with 8K prompts.

**G capture42 → capture 48 stays (item 2 isolated).** The one-line compose edit produced the expected old behaviour ("Truncating max_cudagraph_capture_size to 40", FULL 5/5 on the head, and the same truncation on the worker). c=6 aggregate 122.4 / 119.3 / 128.7 (median 122) vs base2 135.0 / 141.2 / 138.9 and inflight2 134.3 / 143.9 / 139.1: all three trials below base2's minimum, a 12 % loss; c=6 per-stream 25.7 vs 28.8 tok/s. c=1 (55.7 pooled), c=2 (42.4), TTFT (4.5 / 17.9 s), acceptance (26.1 % / 0.71, numbered 53.6 %) and memory (2.86 GB head, 4.44 worker) are unchanged. This is the first direct measurement of report item 2 on this lane: with `MAX_NUM_SEQS=6` and k=6 the decode batch is 42 tokens, and capturing 48 (padded to the 8-multiple) keeps c=6 on a full cudagraph instead of falling to eager or the 40-token graph. Compose line reverted to the padded expression.

**Noise, for the record.** c=1 over 8 trials ranged 47.7–76.5 across boots with medians 53.9–56.6; the two outliers (76.5 greedy, 73.0 capture42) are single-prompt draws, exactly the ±10 tok/s prompt effect noted yesterday. No knob in this sequence moved c=1 beyond that. c=6 aggregate sat at 134–147 on every boot except capture42 (119–129), so the ±10 band is confirmed and the capture42 loss is well outside it.
