# A/B validation, 2026-09-02 — 2× DGX Spark, TP=2 lane (`start-deepseek-v4-flash-dspark.sh`)

Driver: `scripts/ab-measure.sh` (one boot per variable; median-of-3 decode trials, thinking off, p=256; TTFT c=1 at 8K/32K/128K; natural-prose and numbered-word draft acceptance; boot-gate and host-memory checks). Server was down at the start of the session, so the sequence began with a clean baseline boot.

**Outcome: one knob won — `DSPARK_ENABLE_SP_INDEXER=1`; `.env.dspark` ends at the baseline plus that knob (dual-PF, k=6).** The baseline boot did not clear the recovery gate (c=1 ≥ ~60 tok/s and natural pos0 ≥ ~0.85), so the prescribed `baseline-singlepf` diagnostic was run first (tie → dual-PF kept). The session's goal check then required continuing, so B (markov), C (tcdecode) and D (adaptive-chunk) were run one knob per boot against *this session's* baseline: B is correct but gives no speed-up and costs c=6; C regresses c=1; D booted cleanly but head MemAvailable was 2.36 GB after boot, which triggered the goal's hard "< 3 GB → stop the sequence" rule, so D was not measured. After a fresh baseline boot recovered to 4.5 GB the driver's per-boot memory gate let E run: sp-indexer passed ruler-lite 8/8 at 32k/131k and cut cold 128K TTFT by ≈ 6 % with everything else unchanged → ON. F (mtp3) is not bootable on this lane: the launcher enforces k ≥ 5 and k % 3 == 0 for Vision-Exp. Every boot has an extra 5-trial c=1 pass (8 trials total) because the 3-trial spread on this lane is ≈ ±10 tok/s.

## Reasoning per decision

**A → gate failed.** c=1 median 52.4 tok/s (all three trials < 57) against the ≥ ~60 recovery bar, and natural-prose pos0 0.68 against ≥ ~0.85. Everything else was in the reference band: c=6 aggregate 148 (ref 156–162, close), c=2 43 (ref 47–57, slightly low), TTFT 4.5 / 18 / 79 s (ref 4.8 / 18.5–23 / 79–80), numbered-word 47 % (ref 45–51). Important side-finding: the natural-prose acceptance of 25 % / pos0 0.68 was measured with **`DSPARK_ENABLE_REPLICATE_MARKOV=0`**, so the replicated Markov head is *not* the cause of the low natural acceptance seen earlier today (27 % / 0.69 with it ON). The two numbers are the same within noise with the patch off.

**A′ single-PF → tie, reverted.** The first 3-trial pass gave a 65.7 median, but with a 51.5–76.3 spread; a second 5-trial pass on the same boot gave 54.8 (47.7–57.9). Pooled, single-PF c=1 (47.7–76.3) fully overlaps dual-PF (49.8–56.9); c=2, c=6, TTFT at all three lengths, and both acceptance measures differ by less than the trial spread. There is no measured win for single PF, so the fabric selection is not the culprit for the c=1 shortfall and the documented dual-PF configuration was restored. NCCL's NET/IB device choice could not be confirmed from logs (NCCL_DEBUG is not INFO in this env); the A/B is the only evidence. Note the c=1 number depends strongly on which unique cold prompt bench-miaai draws (per-prompt acceptance swings decode 48 → 76 tok/s on the same boot), so the noise band for c=1 on this lane is roughly ±10 tok/s and any knob claiming a c=1 win needs more than 3 trials.

**Natural-prose pos0 gate (≥ 0.85).** Neither boot reached it, with or without the fabric change, and with all of today's opt-in patches off. The 0.85–0.93 expectation traces back to `AUDIT.md` / `scripts/EVAL.md` ("pos0 ~0.93 on good prompts"), while live cumulative `/metrics` readings recorded earlier in `MERGED.md` and `GROK-4.6.md` were already pos0 ≈ 0.78. The 0.68–0.71 seen by `natural-acceptance-window.py` on 8 everyday prompts at c=2 is therefore a pre-existing live-vs-audit gap, not a regression introduced by today's changes. It is still the largest decode lever on the lane (2.5 accepted tokens/step vs ~3.5 at the audit curve) and deserves its own investigation (prompt mix, draft-block size 5 vs k=6, sampling path) before B–F are re-run.

**B markov → OFF (correct, no win).** The correctness check passes: natural-prose acceptance 26.0 % / pos0 0.69 vs baseline 25.2 % / 0.68 at temp 0 (and 0.70 vs 0.68 at temp 0.6), numbered-word 49.5 % vs 47 %. So the replicated head is *not* a bug and the earlier suspicion is cleared. But the promised 1–3 % decode gain did not appear: c=1 pooled ≈ 54 vs 55, c=2 40.5 vs 43.4, and c=6 aggregate median 122 vs 148, with two of three trials (120, 122) below the baseline's worst trial (130). The replicated head also costs 0.44 GiB of head KV. With no target-metric improvement beyond noise, the rule says 0.

**C tcdecode → OFF (regression).** The M≤8 tensor-core decode path made c=1 worse, not better: 8 trials 44.5–60.9, median ≈ 46, versus baseline 49.8–57.9; only one trial (60.9) reached the baseline band. Post-prefill decode at 8K was 45–46 tok/s vs 54–60 on baseline. c=2 and c=6 are flat, so the loss is specific to the M≤8 shape this knob targets. Quality and acceptance are fine. The env var was verified inside the container (`B12X_W4A16_TC_DECODE=1`); there is no boot-log gate for it.

**D adaptive-chunk → OFF (host memory), unmeasured.** Two boots, both with clean gates (patched on both ranks, 6/6 graphs, KV 16.66 / 15.36 GiB), both under the 3 GB line right after boot: head 2.36 GB then 2.28 GB, worker 3.3 GB then 2.50 GB, head sinking to 1.6–1.7 GB idle with 6 GB of swap used. The goal's step 4 rule fired both times, so the measurement was skipped and the knob reverted. On the first attempt I suspected per-restart drift, but the stop released memory back to 116.9 GB (117.7 GB at session start, only ≈ 0.75 GB retained), the very next baseline boot landed at 4.5–4.8 GB, and the second adaptive-chunk boot fell back to 2.3 GB. Every non-adaptive boot this session sat at 3.8–5.2 GB. So the cost is attributable to the knob: adaptive chunking lets prefill run chunks up to `max_num_batched_tokens=8192` instead of 1024, and the larger activation / FlashMLA workspace it warms up lives in unified memory, i.e. host RAM on DGX Spark, outside the `GPU_MEMORY_UTILIZATION_TEXT` budget. Host-side view on the adaptive boot: Cached 4.3–5.4 GB, Shmem 3.7 GB, Slab 3.1 GB (2.7 unreclaimable), AnonPages 2.7–2.9 GB. Without root the shmem/slab owners could not be attributed further. The TTFT target (8K/32K) was never measured because measuring on a swapping host would not be trustworthy.

**E sp-indexer → ON (small but real 128K win, quality intact).** Boot gates clean, `[dspark-sp-indexer] patched` on both ranks, KV 16.54 / 15.87 GiB, MemAvailable 3.6 / 3.7 GB (above the line, lower than baseline's 4.5–5.2 GB). Retrieval: `ruler-lite.py --lengths 32768,131072` passed all eight tasks (sniah, mkniah, vartrack, cwe at both lengths; `results/ruler-lite-sp-indexer-20260902.json`). TTFT: 8K 4.45–4.48 s and 32K 17.8–18.0 s are identical to baseline (below `MIN_KEYS`, as designed); cold 128K 75.95 s in the main run and 74.4 s in a warm repeat, against 78.97 s (A) and 81.24 s (A′) on the two baseline-config boots — both E trials beat both baseline trials by 3–7 s (≈ 4–8 %), outside the 2 s baseline spread. This is far below the design expectation (≈ 1.5–1.8× end-to-end at ≥128K), so the indexer term is a smaller share of the 128K prefill than the item-6 model assumed, or the split path is not the bottleneck at 2 ranks. Decode (c=1 pooled ≈ 55, c=2 41.9, c=6 147), quality probe, natural (25.4 % / 0.68) and numbered-word (51.2 %) acceptance are unchanged; zero EngineDead/NCCL WARN; one extra JIT warning (CuTeDSL `StableTopKFromGatheredCandidatesKernel`, during the acceptance window, not the 128K run). Under the rule (target metric improved beyond noise, everything else unchanged), it stays ON. Note the bench-miaai `--repeat 2` at 131072 reuses its prompt, so its first repeat (3.0 s) is a prefix-cache hit and was discarded.

**F mtp3 → not bootable.** `start-deepseek-v4-flash-dspark.sh` exits 2 before creating a container: "Vision-Exp requires MTP_NUM_TOKENS >= 5 and divisible by 3 (num_nextn_predict_layers=3); got 3". So the only legal values are 6, 9, …; the k=3 experiment cannot be run without changing the launcher, which is out of scope. `results/bootfail-mtp3-{head,worker}.log` hold the driver's capture (no container existed). Reverted to 6.

**Untested always-on suspect.** Cudagraph capture 48 (vs 42) is the only always-on item not isolated by a boot; the fabric (dual-PF) was cleared by A′.
